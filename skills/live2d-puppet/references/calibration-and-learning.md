# 校准证据与学习

## 三种改进对象

项目校准保存某个角色的事实：一个控制点、轴心、网格顶点或权重怎样调整后更自然。软件算法保存跨角色稳定成立的自动推导。Skill 保存 Agent 如何选择工具、检查证据和决定升级层级。三者不能混写。

用户在桌面编辑器保存一次修改后，`calibration/sessions` 会记录前后覆盖、补丁、指纹和 revision，`reports/calibration` 会记录姿态、运动、前后拼图和差异。Agent 用 `history/compare` 读取它们，不要求用户重新描述拖了哪个点。用户的“接受/拒绝”要写入该 session，形成带结果判断的证据。

Agent 自动制作产生的 revision 和 session 走同一条证据链。用户通常只需判断角色结果，并用自然语言说明幅度、延迟、回弹、穿插或轮廓哪里不合适；正式的部位 Agent 或高层 authoring 能承接时直接使用这份反馈，不把它翻译成“请用户自己找点并拖动”。只有公开能力确实无法表达的局部问题才交给桌面校准。

拒绝不是普通的下一轮提示。用户拒绝后必须依次标记本轮所有相关 session 为 `rejected`、恢复最后接受的 revision、复核恢复结果并停止；除非用户给出新的具体方向，不得继续叠加补丁。使用 `record` 时，动态证据还要保存报告中的项目路径、基础 SHA-256、准确 revision、启动时当前 revision 和窗口比例，不能从文件名推测它属于哪个状态；用户不要视频时改用准确 revision 的高清静态、4×4 连续帧和实时窗口，不把 `record` 设成接受/拒绝的前提。

## 从项目到软件

一个角色的接受记录本身不足以修改通用自动绑定算法，但“至少两个项目”不是绝对前置条件。升级软件默认需要证明根因位于可复用的代码、语义识别或几何算法，而不是该角色专属顶点：多个独立项目重复出现同一错误是充分证据；单个真实项目若能用通用代码路径、可复现输入和因果对照证明同样的算法缺陷，也可以修软件。两种情况都必须把修复写成可识别语义而非角色专用顶点列表，增加通用 fixture 或最小复现，并在现有测试 PSD、该真实项目和相关非退化证据上验证。不能证明通用根因时，修改留在项目校准。这个门槛不阻止 Skill 调用用户已经明确批准、软件已经公开提供并经过真实项目验证的整模或分部 Agent 入口，但 Skill 必须准确报告请求 scope、各部位状态、素材缺口和阻断项。修改软件前保存可恢复的代码基线，修改后运行类型检查、构建、单元/集成、Electron 用户链、视觉和性能测试。推送远端只在用户授权范围内执行。

算法问题示例：同类侧发总被归入后发、合并头饰的左右耳根持续定位反了。项目问题示例：某张 PSD 的呆毛根部比 Alpha 自动估计高两个网格点。后者留在项目，不能硬编码进所有角色。

## 从项目到 Skill

只有用户明确要求优化未来 Agent 行为时才修改 Skill，并使用 `$meta-skills`。适合 Skill 的证据是流程层反复犯错，例如只相信测试不看图、把上下看做整体平移、擅自把参考视频加入项目、把一次角色校准当成通用规律。视觉算法本身应改软件，不应塞进更长的提示词来掩盖。

修改 Skill 前先运行 `scripts/file_budget.py <skill-directory>`，提出将改哪些规则/资源及理由，等用户确认后写入；修改后再运行预算、结构验证、契约测试和包装脚本对真实 CLI `--help` 的检查。若任何活动文本超过 9,000 估算 tokens，按单一职责拆分并更新路由，不能删掉必要能力来过门槛。

## 证据最小记录

每次向用户汇报至少包含项目路径、点名部位与自然语言目标、from/to revision、相关 session ID、修改的稳定 ID、参数或 Agent 操作、前后对比路径、采用的静态/实时/动态证据及指纹、安全检查结果和仍未解决的视觉问题。差异图只定位变化，最终判断必须看角色图和对应 revision 的允许证据；还要说明目标部位是否真的产生以源图像像素计可见的连续运动、根部是否稳定，以及未点名区域和历史 accepted 结果是否出现退化。没有实际查看证据时不得说“已经修好”。
